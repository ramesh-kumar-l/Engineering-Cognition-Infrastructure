# ADR-008 — Reflection Engine Domain Model

## Context

Phase 6 adds a Reflection Engine: a subsystem that periodically reviews execution history (goals, tasks, outcomes) and produces typed lesson records. Four design decisions require ratification before implementation.

## Decision 1 — `LessonEvidence` as a separate table (not reusing `ExecutionCitation`)

`ExecutionCitation` stores *retrieval chunks* (chunk_index, score, content snippet) — it models "this retrieval hit motivated this goal." Lesson evidence models "this execution event supports this lesson." The two semantic concepts are different: evidence is coarser (whole goals/tasks, not chunks), has no `chunk_index` or vector `score`, and requires a `summary` field explaining *how* the item supports the claim.

**Decision:** New `lesson_evidence` table with fields: `lesson_id`, `source_type` ('goal'|'task'|'memory_entry'), `source_id` (no FK — polymorphic), `summary`.

## Decision 2 — Lesson supersession via `supersedes_id`

A new lesson that replaces an older one stores `supersedes_id = <old_lesson_id>`. The old lesson's `status` is set to `'superseded'` at that moment. The supersession event is captured as an `AuditEvent` (same as status changes in P5) so the change is auditable without introducing a new audit table.

Forward lookup ("what superseded lesson X?") is done by querying `WHERE supersedes_id = X`, not by storing a back-reference, which would require a deferred constraint or nullable self-FK in both directions.

## Decision 3 — LLM pattern extraction via injected `LLMProvider`

The same `LLMProvider` protocol from P3 is used in the `PatternExtractor` service. Offline-first (AP-3): Ollama is the default provider. The extractor prompts the LLM to return a JSON array of lesson objects; the output is parsed and validated before persistence. If the LLM returns malformed JSON or an empty array, the retrospective still completes (with zero lessons generated by LLM) — the caller can always create lessons manually via `POST /lessons`.

## Decision 4 — Synchronous retrospective runs (no background jobs)

Background job scheduling is P8 scope (CI/CD + SLO infrastructure). `POST /retrospectives` creates and immediately runs the reflection synchronously. The `status` field on `Retrospective` transitions `running → completed | failed` within the same request. This keeps P6 simple and testable without a task queue. Async cadence (cron-based triggering) is recorded as a deferred item in `risk-register/risks.md`.

## Consequences

- New tables: `retrospectives`, `lessons`, `lesson_evidence`.
- `lessons.supersedes_id` is a nullable self-referencing FK.
- LLM malformation is tolerated: a retrospective can complete with zero auto-generated lessons.
- Long-running corpus → slow synchronous run (mitigated by scoping; addressed in P8).
